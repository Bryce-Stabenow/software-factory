# Repository execution configuration

Project command configuration belongs in a versioned `.kulumin.yml` at the repository root. `version: 1` defines `worktree_init` and `verification` command lists. Commands are bounded argv arrays with names and timeouts; no implicit shell is involved. Settings reads the file on opening, imports legacy checks when absent, and writes only on explicit save. Writes use an expected content digest, a same-directory atomic rename, and compensating rollback if the database transaction fails. Symlinks, unsupported YAML features, unknown keys, oversized files and unsupported versions are refused.

Repository trust, execution enablement, implementation limits, authorization of the normalized configuration and initialization network permission remain local SQLite settings. Reading someone else's YAML never grants execution or network access. Execution requires an authorized configuration committed on the default branch for a new worktree, then resolves the file from that worktree's exact committed HEAD. Configuration edits by an implementer cannot silently weaken verification. Settings cannot change during active project runs.

Initialization runs through the existing sandboxed command/exec adapter before implementation. Writes remain bounded to the worktree and private temporary directory; network is enabled only when the YAML requests it and local settings allow it. Verification always disables network. Both stages retain the restricted environment, private HOME, cancellation, timeouts and credential redaction. Hooks may create ignored dependencies and artifacts but source or HEAD mutation blocks progression.

Migration 7 adds initialization history tied to the task, managed worktree, parent run, source SHA, YAML digest and initialization digest. Successful setup is cached per worktree/configuration; failed, cancelled or interrupted setup is retried explicitly with task recovery. A forced initialization recovery reruns setup, checks and independent review without rerunning implementation. Restart never assumes setup succeeded. Setup errors do not enter the bounded code-repair loop.

Verification evidence includes the committed YAML digest and successful initialization record for YAML-configured tasks. Acceptance still reconstructs the exact current commit, checks, independent review and evidence digest. Legacy tasks without YAML keep their original evidence shape so an upgrade alone does not revoke existing final review or acceptance. Saving a new configuration explicitly invalidates existing passing checks and reviewed/accepted tasks when the authorized configuration changes. Git commits, merges and pushes remain human-controlled.
